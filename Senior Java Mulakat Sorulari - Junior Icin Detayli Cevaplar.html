1. Java Memory Management ve Memory Leak

"Java belleği içeride nasıl yönetir? JVM ve garbage collector'ın (çöp toplayıcı) bellek yönetimindeki rolü nedir?"

Mülakatta gelebilecek alt sorular:
  • Kurumsal (enterprise) uygulamalarda memory leak'in yaygın nedenleri nelerdir?
  • JVisualVM, Java Flight Recorder (JFR) ve heap dump gibi araçlarla memory leak nasıl tespit edilir?
  • Object retention (nesne tutulması) nasıl analiz edilir; hangi nesneler garbage collection'ı engelliyor, nasıl bulunur?
  • Bellek kaynaklı production sorunlarını teşhis etmek ve çözmek için hangi stratejiler kullanılır?

Detaylı Cevap

Java'da belleği sen manuel yönetmezsin (C'deki malloc/free gibi). Bunun yerine iki temel oyuncu var:

  • JVM (Java Virtual Machine): Programının çalıştığı ortamdır. Belleği bölgelere ayırır: Heap (nesnelerin yaşadığı yer), Stack (metot çağrıları ve local değişkenler) ve Metaspace (class metadata).
  • Garbage Collector (GC): Heap'te artık kimse referans etmeyen nesneleri bulup temizler. "Bu nesneye kimse ihtiyaç duymuyor mu?" sorusunu reachability (erişilebilirlik) ile cevaplar: GC köklerinden (aktif thread'lerin stack'leri, static alanlar, JNI referansları) başlayarak nesne grafiğini gezer; hiçbir yoldan ulaşılamayan nesne çöp sayılır.

Memory Leak Nedir, Java'da Neden Olur?

"Java'da GC var, nasıl memory leak olur?" — GC, erişilemeyen nesneleri temizler. Ama bir nesne artık kullanılmadığı halde hâlâ erişilebilir ise (yani bir collection, map, cache ya da listener ona referans tutuyorsa), GC onu silemez. İşte bu bir memory leak'tir. Yaygın nedenler:

  • Statik collection'lar: static Map içine sürekli ekleme yapıp silmemek. Uygulama ömrü boyunca büyür.
  • Cache'in sınırsız büyümesi: Eviction (çıkarma) politikası olmayan cache. Çözüm: WeakHashMap, Caffeine/Guava gibi TTL'li cache'ler, ya da LRU politikası.
  • Listener/callback'lerin kaydının silinmemesi: addListener() çağırıp removeListener() yapmamak.
  • ThreadLocal temizlenmemesi: Thread pool'daki thread'ler uzun yaşar; ThreadLocal değerlerini remove() etmezsen, thread yaşadığı sürece nesne heap'te kalır.
  • Kapatılmayan kaynaklar: InputStream, Connection vb. — try-with-resources kullan.
  • Inner class'ların outer'a örtük referansı: Non-static inner class, dış sınıfın instance'ını gizlice referans eder.

Leak Nasıl Tespit Edilir? (Araçlar)

  • JVisualVM: Çalışan uygulamaya bağlanır, heap kullanımını canlı izler. Tipik belirti: Full GC sonrası bile heap kullanımı sürekli yükseliyor, "diş testere" grafiği değil monoton artış görülüyor.
  • Java Flight Recorder (JFR) + Mission Control: Üretimde (production) düşük overhead ile sürekli kayıt tutar; allocation profili, GC davranışı, sıcak noktaları gösterir.
  • Heap dump analizi: jmap -dump:live,format=b,file=heap.hprof <pid> ile ya da -XX:+HeapDumpOnOutOfMemoryError JVM bayrağıyla dump alınır; sonra Eclipse MAT (Memory Analyzer Tool) ile açılır. MAT'ın "Leak Suspects" raporu, en şüpheli nesneleri ve onları tutan referans zincirini (dominator tree + GC roots path) gösterir. "Bu nesneyi kim tutuyor?" sorusunun cevabı leak'in kaynağıdır.

Object Retention Analizi

Heap dump'ta önce hangi nesnelerin en çok yer kapladığını bul (MAT'ta histogram), sonra onlardan GC root'larına giden referans zincirini incele ("Path to GC Roots" — exclude weak/soft references seçeneğiyle). Zincirdeki ilk "sizin kodunuzdan gelen" tutucu genelde suçludur: örn. bir static ConcurrentHashMap ya da bir session nesnesi.

Production Bellek Sorunlarında Strateji

  1. Belirtileri ölç: Grafana/Prometheus ile heap kullanımı, GC süresi, OutOfMemoryError logları.
  2. Leak mi, sadece yüksek yük mü ayırt et: Load azalınca heap geri düşüyor mu?
  3. Heap dump al (HeapDumpOnOutOfMemoryError ideal olarak sorunu önceden yakalar).
  4. MAT ile kök nedeni bul, kodda düzelt.
  5. Yeniden test et: uzun süreli load testi + JFR kaydı.
💡 Junior ipucu: Mülakatta "GC varken nasıl leak olur?" sorusu en sevilen tuzaktır. Kısa cevabı ezberle: "GC erişilemeyen nesneleri temizler; hâlâ erişilebilir ama kullanılmayan nesneler leak olur."

2. JVM Mimarisi ve Garbage Collection

"JVM'in farklı bellek alanlarını ve nasıl çalıştıklarını açıkla."

Alt sorular:
  • Heap Memory, Stack Memory ve Metaspace arasındaki farklar nelerdir?
  • Modern Java sürümlerinde garbage collection nasıl çalışır?
  • G1 GC, ZGC ve Shenandoah GC arasındaki farkları açıkla.
  • Stop-the-World (STW) duraklamaları nedir, performansı nasıl etkiler?
  • Yüksek throughput/düşük latency'li kurumsal uygulama için JVM parametreleri nasıl ayarlanır?

Detaylı Cevap — JVM Bellek Alanları

Heap, nesnelerin "yaşam döngüsüne göre" kuşaklara (generations) ayrılır: Young Generation (Eden + iki Survivor alanı — yeni doğan nesneler burada; çoğu nesne kısa ömürlü olduğu için buradaki GC, yani Minor GC, çok hızlıdır) ve Old Generation (birkaç GC'den sağ kalan uzun ömürlü nesneler). Bir nesne yeterince "yaşlanınca" Old Gen'e terfi eder. Old Gen dolunca Major/Full GC tetiklenir — bu daha yavaştır.

Modern Java'da GC Nasıl Çalışır?

Modern GC'lerin temel fikirleri: (1) generational hypothesis — nesnelerin çoğu gençken ölür; (2) concurrent çalışma — GC işinin büyük kısmını uygulama thread'leriyle eşzamanlı yapar, duraklamayı minimize eder; (3) region-tabanlı heap — heap'i eşit parçalara bölüp her bölgeyi bağımsız toplar. Java 9+ varsayılan GC G1'dir; JDK 21'de Generational ZGC geldi.

Stop-the-World (STW) Nedir?

Bazı GC fazlarında (örn. nesnelerin işaretlenmesi ve taşınması sırasında kısa anlar), JVM tüm uygulama thread'lerini durdurur — dünyaya "dur" der. Bu süre boyunca uygulama hiçbir isteğe cevap veremez. STW süreleri uzunsa (yüzlerce ms — saniyeler): request timeout'lar, health-check düşmeleri, kuyruk birikmesi ve kullanıcı tarafında latency spike'ları görülür. Bu yüzden GC ayarının amacı: pause sürelerini iş ihtiyacına göre sınırlamak.

JVM Ayarlama (Tuning) — Temel Parametreler

java -Xms4g -Xmx4g \                 # heap başlangıcı = maksimum (dalgalanmayı önler)
     -XX:+UseG1GC \                  # GC seçimi (veya UseZGC)
     -XX:MaxGCPauseMillis=50 \       # G1'e "duraklamaları 50ms'de tut" hedefi ver
     -XX:MetaspaceSize=256m \        # metaspace genişleme tetik noktası
     -XX:+HeapDumpOnOutOfMemoryError \   # OOM anında otomatik heap dump
     -XX:HeapDumpPath=/dumps \       # dump yeri
     -Xlog:gc*:file=gc.log:time \    # GC logları (analiz için şart)
     -jar app.jar

İyi pratik: -Xms = -Xmx yapmak (heap'i önceden rezerve et, büyüme anlarında pause olmasın), GC loglarını her zaman açık tutmak, ayarı ölçüme göre yapmak — "körleme -Xmx artırma" değil.

💡 Junior ipucu: "Hangi GC'yi seçerdin?" sorusunda güvenli cevap: "Önce G1 ile başlarım; ölçümlerim düşük latency gerektiriyorsa ve heap büyükse ZGC'yi değerlendiririm. GC seçimi ölçümle yapılır."

3. Multithreading ve Concurrency

"Bir Java uygulamasında verimli çoklu thread ve concurrency nasıl uygulanır?"

Alt sorular:
  • Process ile thread farkı nedir?
  • ExecutorService, CompletableFuture ve ForkJoinPool'u pratik kullanım örnekleriyle açıkla.
  • Yüksek concurrency'li uygulamalarda thread pool'lar nasıl yönetilir?
  • Race condition, deadlock ve thread starvation nedir?
  • Production'da concurrency kaynaklı sorunlar nasıl teşhis edilir?

Process vs Thread

  • Process: Kendi bellek alanına (address space) sahip bağımsız program. İki process birbirinin belleğini doğrudan göremez; iletişim pahalıdır (IPC, socket).
  • Thread: Aynı process içinde çalışan, heap'i paylaşan ama kendi stack'i olan yürütme birimi. Bellek paylaşımı kolay (ve tehlikeli — o yüzden senkronizasyon gerekir). Oluşturulması process'ten çok daha ucuz.

ExecutorService — "Thread'leri Ben Yönetmem, Havuz Yönetir"

Ham new Thread() yerine thread pool kullanılır; thread oluşturma maliyetinden ve sınırsız thread patlamasından kaçınılır.

ExecutorService pool = Executors.newFixedThreadPool(10);
Future<String> f = pool.submit(() -> veriTabaniCagrisi());  // Future ile sonuç bekle
pool.shutdown();  // kapatmayı unutma!

Not: Executors.newFixedThreadPool sınırsız kuyruk kullanır — üretimde genelde doğrudan ThreadPoolExecutor ile sınırlı kuyruk + reddetme politikası (CallerRunsPolicy vb.) tercih edilir.

CompletableFuture — Asenkron Zincirleme

Bir işin sonucu geldiğinde "şunu da yap" demenin modern, okunabilir yolu. Birden çok bağımsız çağrıyı paralel yapıp birleştirmek için idealdir.

CompletableFuture<User> user   = CompletableFuture.supplyAsync(() -> kullaniciGetir(id), pool);
CompletableFuture<List<Siparis>> sip = CompletableFuture.supplyAsync(() -> siparisleriGetir(id), pool);

user.thenCombine(sip, (u, s) -> yeniRapor(u, s))   // ikisi bitince birleştir
    .thenAccept(raporGonder)
    .exceptionally(ex -> { log.hata(ex); return null; });

Pratik kullanım: bir REST endpoint'i kullanıcı + profil + öneri verisini üç ayrı servisten paralel çekmek (sıralı çağırırsan 3× latency, paralelde max tek çağrı süresi).

ForkJoinPool — "Böl ve Yönet" Paralellizmi

Büyük işi küçük alt işlere bölüp (fork) sonuçları birleştiren (join) havuz; work-stealing ile boşta kalan thread'ler diğerlerinin kuyruğundan iş çalar. parallelStream() arka planda ortak (common) ForkJoinPool'u kullanır. Dikkat: parallelStream içinde blocking I/O yapma — ortak havuzu kilitlersin, uygulama genelinde yavaşlar.

Thread Pool Yönetimi (Yüksek Concurrency)

  • Boyutlandırma: CPU-bound işler için ~ CPU çekirdek sayısı; I/O-bound işler için daha fazla (çünkü thread'ler çoğu zaman bekler). Kural olarak N_cpu * (1 + bekleme/hesaplama oranı).
  • Tek ortak havuz yerine iş türüne göre ayrı havuzlar (I/O çağrıları için bir havuz, CPU işleri için başka) — bulkhead ilkesi, tıkanmanın yayılmasını önler.
  • Sınırlı kuyruk + reddetme politikası: Kuyruk dolduğunda ne olacak? AbortPolicy (hata fırlat), CallerRunsPolicy (gönderen thread çalıştırır — doğal geri basınç/backpressure), DiscardPolicy (sessizce at — genelde kötü).
  • Thread isimlendirme: Loglarda/thread dump'ta teşhisi kolaylaştırır (ThreadFactory ile).
  • Graceful shutdown: shutdown() + awaitTermination.

Klasik Üç Düşman: Race Condition, Deadlock, Starvation

  • Race condition: Sonucun, thread'lerin işlemleri hangi sırada yaptığına bağlı olması. Klasik örnek: iki thread'in aynı counter++'yı yapması (okuma-artırma-yazma atomik değil). Çözüm: senkronizasyon veya atomic sınıflar.
  • Deadlock: İki thread birbirinin tuttuğu kilidi bekleyip sonsuza kadar kilitlenmesi. Koşul: sırayla iki kilit alınır, iki thread ters sırada alır. Çözüm: kilitleri her yerde aynı sırada al; mümkünse tryLock(timeout) kullan.
  • Thread starvation: Bir thread, kaynaklara (CPU, kilit, havuzdaki slot) erişemeyip aç kalır. Örn. yüksek öncelikli işler kilidi sürekli tutunca düşük öncelikli iş aç kalır; ya da kuyrukta sona kalan istek hiç sırası gelmez.

Production'da Concurrency Sorunu Teşhisi

  • Thread dump al (jstack <pid> ya da kill -3): BLOCKED durumunda kilit bekleyen thread'ler ve deadlock tespiti (JVM "Found one Java-level deadlock" yazar). İki-üç dump'ı 10 sn arayla alıp karşılaştırmak "hangi kilit sürekli tutuluyor" sorusunu cevaplar.
  • Pool metrikleri: aktif thread sayısı, kuyruk boyutu, reddedilen görev sayısı → Metrikleri Prometheus'a aktar.
  • JFR: Lock contention ve thread park olaylarını düşük maliyetle kaydeder.
💡 Junior ipucu: Mülakatta CompletableFuture örneği istenebilir. "İki bağımsız servisi paralel çağırıp thenCombine ile birleştiririm" demek + küçük bir kod yazmak çok etkileyicidir.

4. Synchronization ve Thread Safety

"synchronized, ReentrantLock, volatile ve Atomic değişkenler arasındaki farkları açıkla."

Alt sorular:
  • synchronized anahtar kelimesi içeride nasıl çalışır?
  • ReentrantLock'un synchronized'a göre avantajları nelerdir?
  • volatile anahtar kelimesinin amacı nedir?
  • AtomicInteger ve diğer atomic sınıflar thread-safe işlemleri nasıl garantiler?
  • Yüksek concurrency'li uygulamada hangi yaklaşımı ne zaman seçerdin?

synchronized İçeride Nasıl Çalışır?

JVM seviyesinde her nesnenin bir monitor (intrinsik kilit) vardır. synchronized(obj) { ... } bloğuna giren thread o monitörü sahiplenir; çıkarken bırakır. Modern JVM'de kilit ilk başta hafif moddadır: biasing/spinning (kısa süre meşgul bekleme) dener, rekabet artarsa OS seviyesine (mutex) yükseltir (lock inflation). Ayrıca reentrant'tir: aynı thread kilidi yeniden alabilir (kaç kez aldıysa o kadar bırakır).

ReentrantLock'un Avantajları

private final ReentrantLock lock = new ReentrantLock();

void islem() {
    if (lock.tryLock(100, TimeUnit.MILLISECONDS)) {  // beklerken vazgeçebilirim
        try {
            // kritik bölge
        } finally {
            lock.unlock();   // synchronized'de bu otomatikti, burada SEN sorumlusun
        }
    } else {
        // kilidi alamadım — farklı bir yol izle (hızlı geri dönüş)
    }
}
  • tryLock(timeout) — sonsuz beklemeyi engeller, deadlock'a karşı savunma.
  • lockInterruptibly() — beklerken interrupt edilebilir (deadlock'tan kurtulma yolu).
  • new ReentrantLock(true) — fair lock: bekleme sırasına saygı gösterir, starvation'ı azaltır (ama throughput düşürür).
  • Condition — birden fazla bekleme/uyandırma kuyruğu (birden çok wait/notify grubu).

volatile Ne Yapar, Ne Yapmaz?

Sorun şudur: her thread performans için değişkenleri CPU cache'inde tutabilir; bir thread'in yazdığı değer diğerine gecikmeli ulaşır. volatile der ki: "Bu değişkene her yazma doğrudan ana belleğe gitsin, her okuma ana bellekten gelsin; ayrıca komutlar yeniden sıralanmasın." Yani görünürlük garantisi verir. Ama i++ gibi okuma+yazma kombinasyonlarını atomik yapmaz — iki thread aynı anda 5 okuyup 6 yazabilir, sonuç 6 olur (7 yerine).

Atomic Sınıflar ve CAS

AtomicInteger.incrementAndGet(), kilit kullanmadan CAS (Compare-And-Swap) donanım komutuyla çalışır: "Değer hâlâ 5 ise 6 yap." Başarısız olursa (o arada başka thread değiştirmişse) işlemi tekrar dener (spin). Kilit yoktur, thread bloklamaz; rekabet azsa synchronized'den hızlıdır. Ayrıca AtomicReference + compareAndSet ile kilitsiz veri yapıları yazılabilir.

Hangi Durumda Hangisi? (Karar Kılavuzu)

  • Tek bir boolean/int bayrak, sadece görünürlük → volatile
  • Sayma/ sayaç gibi tek değişkenli atomik güncelleme → AtomicInteger/LongAdder (yüksek rekabette LongAdder daha iyi)
  • Birden fazla değişkenin birlikte güncellenmesi, kritik bölge → synchronized (basitse) ya da ReentrantLock (timeout/fair/interrupt gerekiyorsa)
  • Paylaşılan collection → ConcurrentHashMap gibi concurrent koleksiyonlar (kendi kilidini yazma!)
💡 Junior ipucu: "volatile atomiklik sağlar mı?" sorusu klasik tuzaktır. Cevap: "Hayır, sadece görünürlük. Atomik artırma için Atomic sınıflar kullanılır."

5. Spring Boot ile Microservices Mimarisi

"Java, Spring Boot ve Spring Cloud kullanarak ölçeklenebilir ve dayanıklı (resilient) bir microservices mimarisi nasıl tasarlanır?"

Alt sorular:
  • Microservices tasarlarken servis sınırları (boundaries) nasıl belirlenir?
  • Servisler REST API ve asenkron mesajlaşma ile nasıl iletişim kurar?
  • API Gateway ve service discovery'nin rolü nedir?
  • Merkezi konfigürasyon yönetimi nasıl uygulanır?
  • Circuit breaker, retry, timeout ve bulkhead pattern'lerini açıkla.
  • Birden çok microservice arasında veri tutarlılığı nasıl sağlanır?

Servis Sınırları Nasıl Belirlenir?

Altın kural: servisler iş yeteneğine (business capability) göre bölünür — tabloların/teknolojinin değil. "Sipariş", "Ödeme", "Stok", "Bildirim" gibi. Domain-Driven Design'ın Bounded Context kavramı: her servisin kendi modeli ve kendi veritabanı vardır (database-per-service — bir servisin tablosuna doğrudan başka servisten SQL atılmaz). Kaba bir test: "Bu servisi silersem hangi işlev gider?" — cevap tek ve net bir işlevse sınır doğrudur.

İletişim: Senkron (REST) vs Asenkron (Mesajlaşma)

  • Senkron REST/gRPC: Cevabın hemen gerekli olduğu yerlerde (örn. ödeme onayı). Dezavantaj: çağrılan servis yavaşsa sen de yavaşlarsın (zincirleme arıza riski).
  • Asenkron mesajlaşma (Kafka, RabbitMQ): Olay (event) yayını — "SiparişOluşturuldu" event'ini yayınlar; stok ve bildirim servisleri dinler. Servisler birbirini tanımaz (loose coupling), birinin yavaşlaması diğerini kilitlemez. Event-driven mimarinin temelidir.

API Gateway ve Service Discovery

  • API Gateway (Spring Cloud Gateway): Tüm dış isteklerin tek kapısı. Routing, authentication/authorization (token doğrulama), rate limiting, SSL sonlandırma, istek birleştirme. İstemciler iç topolojiyi bilmez.
  • Service Discovery (Eureka, Consul, Kubernetes DNS): Container ortamında servis adresleri sürekli değişir. Servisler ayağa kalkınca kendini registry'ye kaydeder; çağıran taraf isimle arar. Kubernetes'te bu iş built-in DNS/service ile zaten çözülür.

Merkezi Konfigürasyon (Spring Cloud Config)

Config'ler (veritabanı adresi, feature flag'ler) Git'te tutulur; Spring Cloud Config Server bunları servis eder; her servis boot sırasında kendi profil config'ini çeker. spring-cloud-bus + @RefreshScope ile çalışırken config güncellenebilir. Kubernetes dünyasında alternatif: ConfigMap + Secret.

Dayanıklılık (Resilience) Pattern'leri — Resilience4j

PatternNe işe yarar
Circuit BreakerBir servise çağrılar sürekli hata veriyorsa, "devreyi aç": bir süre çağrıları hiç deneme, hemen fallback dön. Servisi toparlanmak için korur; kilitlenme zincirini (cascading failure) kırar.
RetryGeçici hataları (timeout, kısa 5xx) üstel geri çekilme (exponential backoff) ile tekrar dene. Idempotent olmayan işlemlerde dikkat: tekrar denemek çift kayıt yaratabilir.
TimeoutHer dış çağrıya üst sınır koy. Timeout'suz çağrı, thread'leri sonsuza kadar bloklar.
BulkheadKaynakları bölmek gemideki su geçirmez bölmeler gibi: ödeme servisinin havuzu tıkansa bile, kullanıcı profili çağrıları etkilenmesin (ayrı thread pool / ayrı bağlantı havuzu).

Mikroservislerde Veri Tutarlılığı

Her servisin kendi DB'si varken klasik ACID transaction'ı imkânsızdır. Cevap: Saga pattern — dağıtık işlem, yerel işlemler + telafi (compensation) adımlarına bölünür. Örn. "Ödeme al → Stok düş → Sipariş oluştur" zincirinde stok düşemezse: ödemeyi iade et. İki yaklaşım: choreography (her servis event'leri dinler, merkezi koordinatör yok) ve orchestration (bir koordinatör servis adımları yönetir). Ayrıca eventual consistency gerçeğini kabullenmek ve outbox pattern (DB'ye işlemin kaydı ile event'i aynı transaction'da yazmak, sonra async yayınlamak — "event kaybolması" sorununu çözer) kritik detaylardır.

💡 Junior ipucu: "Her şeyi microservice yaparım" demek junior göstergesidir. Ekleyecegin cümle: "Önce modüler monolith başlatıp sınırlar netleşince ayırırım; microservice, operasyonel maliyeti yüksek bir mimari kararıdır."

6. Java Application Performance Optimization

"Bir Java uygulamasında yüksek CPU kullanımı, artan bellek tüketimi ve yavaş veritabanı sorguları var. Nasıl araştırır ve optimize edersin?"

Alt sorular:
  • Thread dump ve profiling araçlarıyla CPU darboğazları nasıl tespit edilir?
  • Bellek tüketimi ve GC aktivitesi nasıl analiz edilir?
  • Yavaş SQL sorguları ve DB darboğazları nasıl tespit edilir?
  • Caching, connection pooling ve sorgu optimizasyonu için hangi teknikler kullanılır?
  • Ağır trafik altında response time ve throughput nasıl iyileştirilir?

Adım Adım Teşhis Yöntemi

  1. Ölçmeden kod değiştirme. Önce belirtileri nicelleştir: hangi endpoint, hangi saatte, ne kadar?
  2. CPU yüksekse → thread dump al (aynı anda 2-3 tane, 5-10 sn arayla). Çoğu dump'ta tekrar tekrar aynı stack'te görünen thread'ler suçludur: döngü, regex backtracking, hashing, JSON parse... Alternatif: async-profiler veya JFR ile flame graph çıkar — hangi metot CPU yiyor tek görselde görünür.
  3. Bellek artıyorsa → GC logları + heap analizi: GC frekansı/süresi artıyor mu? Full GC'ler sıklaştıysa heap baskısı var. Heap dump al, MAT ile en büyük nesneleri bul (histogram + dominator tree). "Leak mi, yetersiz heap mi, gereksiz büyük nesne üretimi mi?" ayrımı yap.
  4. DB yavaşsa → sorgu izleme: Hibernate show_sql yerine p6spy/statistics; ya da DB tarafında EXPLAIN ANALYZE / slow query log. N+1 sorgu problemine bak (aşağıda).

CPU Darboğazları — Pratik Araçlar

  • Thread dump: jstack <pid> — RUNNABLE thread'lerin stack'lerini karşılaştır.
  • async-profiler: sampling tabanlı, düşük overhead; flame graph üretir.
  • JFR (Java Flight Recorder): üretimde güvenle çalışır; "hot methods" ve CPU örneklemesi.
  • VisualVM / IntelliJ Profiler: geliştirme/staging ortamında.

Bellek ve GC Analizi

  • GC loglarını -Xlog:gc* ile aç, gceasy.io gibi araçlarla yorumla. Metrikler: GC frekansı, ortalama/maks pause, promotion oranı.
  • Heap dump'ta beklenmedik büyük tutucular mı var? (örn. 1 milyon adet UserDto cache'te birikmiş)
  • Gereksiz nesne üretimini azalt: string birleştirmek yerine StringBuilder, gereksiz büyük page-size, stream içinde gereksiz ara collection'lar.

Yavaş Sorgular ve DB Optimizasyonu

  • EXPLAIN/EXPLAIN ANALYZE ile sorgu planını incele: seq scan mi yapıyor, index kullanıyor mu?
  • Eksik index'leri ekle (WHERE, JOIN, ORDER BY kolonlarına); fakat her index yazma performansını da yavaşlatır — dengeli ol.
  • N+1 problemine dikkat: 100 sipariş için 100 ayrı SELECT * FROM customer sorgusu. Çözüm: JOIN FETCH, @EntityGraph, batch fetching.
  • Sadece lazım olan alanı çek: SELECT * yerine projection/DTO sorguları.
  • Connection pool ayarı: HikariCP'nin pool boyutu DB kapasitesine göre; default'lara körlemesine güvenme. Pool tükendiyse (loglarda "connection timeout") istekler kuyrukta bekler — bu da "yavaş API" olarak görünür.

Caching

  • Katmanlar: Uygulama içi (Caffeine) → dağıtık (Redis) → HTTP cache (ETag, Cache-Control) → CDN.
  • Ne cache'lenir: nadir değişen, sık okunan veri (ürün kataloğu, konfig, referans veriler). Ne cache'lenmez: gerçek-zamanlı bakiye gibi hassas/gerçek zamanlı veriler.
  • TTL + invalidation stratejisi düşün: veri değişince cache nasıl güncellenir? (event ile invalidation)
  • Spring'te: @Cacheable, @CacheEvict.

Ağır Trafik Altında Yanıt Süresi ve Throughput

  • Bağımlı çağrıları paralelleştir (CompletableFuture).
  • Yazma yollarını asenkron yap (mesaj kuyruğu); kullanıcı beklemesin, event arkada işlensin.
  • Yanıt küçült (gereksiz alan döndürme), gzip/HTTP2, sayfalama.
  • Load shedding / rate limiting ile koruma; ölçüm (p95/p99 latency) olmadan "iyileşme" iddia etme.
💡 Junior ipucu: Bu sorunun asıl test ettiği şey metodolojidir. Cevabın "X'i optimize ederim" değil, "önce ölçerim, sonra suçluyu bulurum, sonra o noktayı düzeltirim" mantığıyla ilerlemelidir.

7. Spring Boot Transaction Management

"Spring Boot'ta transaction yönetimi nasıl çalışır? Açıkla."

Alt sorular:
  • @Transactional anotasyonunun amacı nedir?
  • Propagation seviyelerini açıkla: REQUIRED, REQUIRES_NEW, SUPPORTS.
  • Transaction isolation seviyeleri nedir; dirty read, non-repeatable read, phantom read'i nasıl önler?
  • Transactional metot içinde exception olursa ne olur?
  • Neden self-invocation'da (kendi metodunu çağırma) @Transactional çalışmaz?
  • Birden çok microservice arasında transaction nasıl yönetilir?

Detaylı Cevap — @Transactional Temelleri

Spring, @Transactional metotlarını AOP proxy üzerinden sarar: metodu çağırmadan önce transaction açar (commit/rollback'i yönetir), metot bitince commit eder, unchecked exception atılınca rollback yapar.

@Service
public class SiparisServisi {

    @Transactional
    public void siparisOlustur(SiparisDto dto) {
        siparisRepo.save(dto.toEntity());   // hepsi ya hep ya hiç (all-or-nothing)
        stokRepo.stokDus(dto.getUrunId());
        odamRepo.kayitEkle(dto);
    }   // metot sorunsuz biterse COMMIT; RuntimeException → ROLLBACK
}

Önemli not: Varsayılan rollback sadece RuntimeException (ve Error) içindir. Checked exception'da rollback olmaz! İstersen: @Transactional(rollbackFor = Exception.class).

Propagation (Yayılım) Seviyeleri

SeviyeAnlamı
REQUIRED (varsayılan)"Transaction varsa ona katılır, yoksa yeni açar." En yaygın kullanım.
REQUIRES_NEW"Her durumda KENDİ yeni transaction'ımı aç." Dış transaction rollback edilse bile içteki bağımsız commit olur. Kullanım: audit log — iş başarısız olsa bile log kaydı kalsın.
SUPPORTS"Varmışsa katılırım, yoksa transaction'sız çalışırım." Transaction opsiyoneldir.
MANDATORY"Zaten açık bir transaction OLMALI, yoksa hata."
NEVER"Transaction OLMAMALI, varsa hata."

Isolation Seviyeleri ve Eşzamanlılık Anomalileri

  • Dirty read: Başka bir transaction'ın henüz commit etmemiş (ileride geri alınabilecek) verisini okumak.
  • Non-repeatable read: Aynı transaction içinde aynı satırı iki kez okuyup farklı sonuç almak (arada başka biri UPDATE edip commit etti).
  • Phantom read: Aynı sorguyu iki kez çalıştırınca satır sayısının değişmesi (arada biri INSERT/DELETE etti).
IsolationDirty readNon-repeatablePhantom
READ_UNCOMMITTEDolur ⚠olur ⚠olur ⚠
READ_COMMITTED (çoğu DB default'u)önlenirolur ⚠olur ⚠
REPEATABLE_READönlenirönlenirolur ⚠ (MySQL InnoDB'de önlenir)

Isolation yükseldikçe güvenlik artar, paralellik/performans düşer. Bu yüzden varsayılan çoğu zaman en mantıklısıdır; sadece gerçek ihtiyaç olan yerde yükselt.

Exception Olursa Ne Olur?

Varsayılan: unchecked exception (RuntimeException) → rollback; checked exception → commit. Ayrıca sadece o metot değil, tümmetot geri alınır (tek transaction'dakiler). rollbackFor/noRollbackFor ile ayarlanabilir.

Self-Invocation Tuzağı (Çok Sevilen Soru!)

@Service
public class Servis {
    public void disMetot() {
        icMetot();          // ⚠️ @Transactional ÇALIŞMAZ!
    }

    @Transactional
    public void icMetot() { ... }

Neden? Spring transaction'ı proxy üzerinden uygular. disMetot()'a dışarıdan çağrı geldiğinde proxy devreye girer; ama içerideki icMetot() çağrısı proxy'den değil, doğrudan this üzerinden yapılır — proxy araya giremez, transaction açılmaz. Çözümler: metodu başka bir bean'e taşı, self-injection (proxy üzerinden çağır) veya AspectJ modu. Aynı şekilde private/final metotlardaki @Transactional da çalışmaz (proxy override edemez).

Microservices Arası Transaction

Tek DB transaction'ı olamaz → Saga pattern, outbox pattern, idempotent consumer'lar ve eventual consistency (bkz. Soru 5).

💡 Junior ipucu: İki tuzak soruyu mutlaka bil: (1) checked exception'da default rollback YOK, (2) self-invocation'da @Transactional ÇALIŞMAZ. İkisi de "Spring'i gerçekten anlıyor musun?" testidir.

8. Java Collections'ın İç Çalışması

"HashMap, ConcurrentHashMap, TreeMap ve LinkedHashMap'in iç implementasyonunu ve farklarını açıkla."

Alt sorular:
  • HashMap içeride nasıl çalışır?
  • Modern Java'da hash collision nasıl yönetilir?
  • HashMap ile ConcurrentHashMap farkı nedir?
  • ConcurrentHashMap concurrent erişimi nasıl destekler?
  • HashMap yerine TreeMap ne zaman kullanılır?
  • LinkedHashMap ekleme sırasını nasıl korur?
  • Bu collection'larda yaygın işlemlerin time complexity'si nedir?

HashMap İçeride Nasıl Çalışır?

  1. put(key, value) çağrıldığında önce key'in hashCode() hesaplanır, sonra JVM bunun üzerine bir karıştırma (spreading) fonksiyonu uygular (yüksek bitleri aşağı kaydırır) — dağılımı iyileştirmek için.
  2. Bu hash değeri (n - 1) & hash ile bucket indeksine çevirilir (n = tablo boyutu, hep 2'nin kuvveti — böylece mod alma yerine hızlı bit maskesi kullanılır).
  3. Bucket boşsa düğüm (Node) koyulur; doluysa aynı bucket'taki elemanlarla equals() ile karşılaştırılır; aynı key varsa value güncellenir, yoksa zincire eklenir.
  4. Resize: Eleman sayısı capacity × loadFactor (default 16 × 0.75 = 12) aşarsa tablo ikiye katlanır ve tüm elemanlar yeniden dağıtılır — maliyetli bir işlemdir, bu yüzden bilinen büyük boyut için new HashMap<>(beklenenSayi) ile kapasite vermek iyi pratiktir.

Kritik sözleşme: equals()'i override edersen hashCode()'u da override etmelisin. Aksi halde "eşit" iki key farklı bucket'lara düşer ve Map'te ikisi de ayrı kayıt olarak durur — çok klasik bug.

Hash Collision Modern Java'da (Java 8+): Treeify

Aynı bucket'ta çok eleman birikirse (collision kötüyse) çift yönlü zincir kırmızı-siyah ağaca dönüşür: zincir uzunluğu 8'e ulaşır VE tablo boyutu ≥ 64 ise treeify olur. Böylece en kötü durum O(n)'den O(log n)'e iner (hash tabanlı DoS saldırılarına karşı da savunma). Zincir 6'nın altına inince tekrar listeye döner.

ConcurrentHashMap Nasıl Eşzamanlı Erişim Sağlar?

  • Java 7'de Segment yaklaşımı vardı (16 ayrı kilit). Java 8'de bu gitti: artık her bucket ilk düğümüne CAS + synchronized uygular — yani iki thread farklı bucket'lara yazıyorsa bibirbirini hiç bloklamaz. Aynı bucket'a yazıyorlarsa sadece o bucket kilitlenir (fine-grained locking).
  • Okumalar kilitsizdir (volatile tablolar) — okuma tarafında synchronized yok.
  • Kompozit atomik işlemler: putIfAbsent, computeIfAbsent, compute — "kontrol et sonra koy" iki adımının atomik yapılmasını sağlar. (Yoksa containsKey + put ikilisi race condition'dır.)
  • size() bile özel bir teknikle (counter'ların dağıtık tutulması) kilit contention'ı azaltır.

TreeMap Ne Zaman?

TreeMap Red-Black Tree (dengeli BST) tabanlıdır; veriyi sıralı tutar. firstKey(), lastKey(), floorKey(), headMap(), tailMap() gibi sıra tabanlı aramalar gerekince kullanılır (örn. "belli bir tarihten önceki en yakın kaydı bul"). get/put O(log n) — HashMap'in O(1)'inden yavaş, ama sıralı erişim bedava gelir. Key sınıfı Comparable olmalı ya da Comparator vermelisin.

LinkedHashMap: Ekleme Sırası Nasıl Korunur?

Her düğüm, ekstra before/after işaretçileri taşır; tüm girişler çift yönlü bağlantılı liste olarak da bağlanır. Böylece iterasyon her zaman ekleme (veya erişim) sırasındadır. Bonus: accessOrder=true ile "en son erişilen en sona gider" modu — bu, LRU cache yazmak için hazır temeldir: LinkedHashMap'i extend edip removeEldestEntry()'yi override etmek klasik mülakat sorusudur.

9. Java Application Security (Spring Security)

"Kurumsal bir Java uygulamasında REST API'ler Spring Security ile nasıl güvenli hale getirilir?"

Alt sorular:
  • Spring Security'de authentication ve authorization nasıl çalışır?
  • JWT tabanlı authentication ve token doğrulamayı açıkla.
  • OAuth 2.0 ile OpenID Connect arasındaki fark nedir?
  • Role-based ve metot seviyesinde erişim kontrolü nasıl uygulanır?
  • API'ler CSRF, CORS yanlış yapılandırması ve yetkisiz erişime karşı nasıl korunur?
  • Access token, refresh token ve hassas credential'lar için en iyi pratikler nelerdir?

Authentication vs Authorization (Spring Security'nin İşleyişi)

  • Authentication (kimlik doğrulama): "Sen kimsin?" — credential doğrulama. Spring Security'de istek FilterChain'den geçer: her istek bir filtre zincirinden (SecurityFilterChain) geçer; kimlik filtreleri (örn. JWT filtresi) token'ı çözer ve SecurityContext'e Authentication nesnesi koyar.
  • Authorization (yetkilendirme): "Bu işi yapmaya yetkin var mı?" — rol/authority kontrolü. URL bazlı (requestMatchers("/admin/**").hasRole("ADMIN")) ve metot bazlı olabilir.
@Configuration
public class GuvenlikKonfig {
    @Bean
    SecurityFilterChain chain(HttpSecurity http) throws Exception {
        return http
            .csrf(csrf -> csrf.disable())                      // stateless API'de CSRF kapalı
            .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**").permitAll()
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .addFilterBefore(jwtFiltresi, UsernamePasswordAuthenticationFilter.class)
            .build();
    }
}

JWT Authentication Nasıl Çalışır?

  1. Kullanıcı login olur → sunucu imzalı bir JWT üretir (3 bölüm: header.payload.signature). Payload'da claims var: sub (kullanıcı), roles, exp (bitiş zamanı).
  2. İstemci her istekte token'ı Authorization: Bearer <token> başlığıyla gönderir.
  3. Sunucu (stateless): imzayı gizli anahtarla (HMAC) ya da public key ile (RSA/ECDSA) doğrular, exp'e bakar, geçerliyse claim'lerden kullanıcıyı kurar. DB'ye session bakmaya gerek yok — ölçeklenebilirliğin ana nedeni budur.
  4. Doğrulama tipik olarak bir custom filter'da yapılır (yukarıdaki jwtFiltresi), sonra normal yetkilendirme akışı devam eder.

Dikkat: JWT'nin zayıf yanıtı iptal (revocation) edilememesidir — token geçerlilik süresi bitene kadar geçerlidir. Çözüm: kısa ömürlü access token + refresh token + gerekirse blacklist.

OAuth 2.0 vs OpenID Connect

  • OAuth 2.0 = yetkilendirme (authorization) çerçevesi: "Bu uygulama, benim adıma API'lerime erişebilir." Access token üretir; ama kimlik bilgisi taşımaz.
  • OpenID Connect (OIDC) = OAuth 2.0 üstüne kimlik katmanı: id_token (yine JWT) ile "bu kullanıcı kimdir" bilgisini standartlaştırır. "Google ile giriş" dediğinde aslında OIDC kullanıyorsun.
  • Kısa cevap formülü: "OAuth 2.0 yetkiye, OIDC kimliğe yarar; OIDC, OAuth 2.0'ın üstünde çalışır."

Role-Based ve Metot Seviyesinde Yetki

// Metot seviyesi
@PreAuthorize("hasRole('ADMIN')")
public void kullaniciSil(Long id) { ... }

@PreAuthorize("#id == authentication.principal.id or hasRole('ADMIN')")
public Kullanici profilGetir(Long id) { ... }   // SpEL ile nesne bazlı kural bile yazılır

Etkinleştirmek için @EnableMethodSecurity gerekir.

CSRF, CORS, Yetkisiz Erişim

  • CSRF: Tarayıcının otomatik cookie göndermesinden yararlanan saldırı. Stateless JWT API'de gerek yok (cookie ile otomatik auth yok) → disable edilebilir. Ama session/cookie tabanlı uygulamada zorunlu; Spring Security'nin CsrfFilter'ı token'ı otomatik yönetir.
  • CORS: Tarayıcının başka origin'e istek politikası. Sunucu tarafında açıkça tanımlanmalı (CorsConfigurationSource): hangi origin, hangi metot, hangi header. * (herkese açık) + credential'lara izin vermek klasik güvenlik açığıdır.
  • Yetkisiz erişim: Varsayılanı "her şey kapalı" yap (anyRequest().authenticated()), sonra tek tek aç. Ayrıca IDOR'a dikkat: "kullanıcının kendi kaydına mı bakıyor" kontrolü (bkz. yukarıdaki @PreAuthorize örneği) — rol yetse bile sahiplik kontrolü gerekir.

Token ve Credential Yönetimi — En İyi Pratikler

  • Kısa ömürlü access token (5-15 dk) + daha uzun ömürlü refresh token (rotate ederek — her yenilemede eski refresh geçersiz olur, token theft'i tespit etmeye yardımcı olur).
  • Secret'ları asla kodda/env'e düz metin yazma: Vault / AWS Secrets Manager / K8s Secret. application.yml'e şifre koymak en yaygın junior hatasıdır.
  • Şifre saklama: BCrypt/Argon2 gibi yavaş hash — MD5/SHA-256 asla.
  • Transport güvenliği: HTTPS everywhere, HSTS.
  • Loglara token/şifre/kimlik numarası yazma; rate limiting ile brute-force koruması; başarısız girişlerde hesap kilitleme/uyarı.
💡 Junior ipucu: "JWT'i nerede saklarsın?" sorusu da çok gelir. Tarayıcıda localStorage XSS riski taşır; httpOnly cookie daha güvenli ama CSRF'e karşı önlem ister. Bu trade-off'u bilmek puan kazandırır.

10. Gerçek Production Sorunu ve Sorun Giderme

"Büyük ölçekli bir kurumsal Java uygulamasında karşılaştığın zor bir production sorununu anlat." (Davranışsal/mülakat hikâyesi sorusu — STAR formatında cevaplanır)

Alt sorular:
  • Sorunun iş ve teknik etkisi neydi?
  • Kök nedeni nasıl tespit ettin?
  • Hangi debugging, monitoring ve profiling araçlarını kullandın?
  • Çözüm olarak ne uyguladın?
  • Yeni sorun yaratmadan düzeltmeyi nasıl doğruladın?
  • Benzer olayların tekrarını önlemek için ne yaptın?

Detaylı Cevap — Junior için Cevap Çatısı (STAR)

Bu soruda gerçek hikâyen yoksa bile, yapı öğrenip örnek bir hikâye anlatabilirsin. Aşağıda gerçekçi bir örnek hikâye + her adımda mülakatçının aradığı şey var.

S — Situation (Durum)

"Sipariş servisimiz, akşam yoğun saatinde (peak saatlerde) yanıt süreleri p95 olarak 200ms'den 8 saniyeye çıktı; bazı istekler timeout oldu ve müşteri tarafında 'sipariş verilemiyor' şikayetleri arttı."

Aradığı şey: etkiyi iş diliyle anlatabilmen. "CPU 90%'ydı" demek yetmez; müşteri/gelir etkisini söyle.

T — Task (Görev)

"Ekibimde kök neden analizi ve düzeltmeden ben sorumluydum; mümkün olan en kısa sürede hizmeti geri getirip kalıcı çözümü üretmem gerekiyordu."

A — Action (Aksiyon) — asıl önemli kısım

  1. Önce kalıcı izleme: Grafana'da p95 latency, hata oranı, JVM metrikleri (heap, GC süresi, aktif thread), DB connection pool kullanımı grafiklerine baktım. GC süresi normaldi → memory değildi. Connection pool bekleyen istekler yükseliyordu → ilk ipucu.
  2. Thread dump: jstack ile iki dump aldım; onlarca thread HikariPool içinde getConnection bekliyordu ve bir tane thread'in stack'i tek bir yavaş SQL sorgusunda takılıydı.
  3. DB tarafı: Slow query log + EXPLAIN ANALYZE → siparis tablosunda yeni eklenen bir sorgu, olusturma_tarihi üzerinde index olmadan full scan yapıyordu; tablo büyüdükçe sorgu giderek yavaşlıyordu.
  4. Araçlar kullandım: jstack (thread dump), JFR (kısa kayıtla doğrulama), Grafana/Prometheus (metrikler), DB'nin slow query log'u ve EXPLAIN.
  5. Çözüm: Acil: eksik index eklendi (online index creation ile, lock'lamadan). Kalıcı: o sorgunun kodu review'landı, N+1 riski giderildi; connection pool metriklerine alarm kuruldu.

R — Result (Sonuç) ve Doğrulama

  • "Index sonrası p95 8s → 250ms'e döndü; pool bekleyen istek sıfırlandı."
  • Doğrulama: Düzeltmeyi önce staging'de üretim verisi boyutunda kopyayla test ettik; load testi (k6/JMeter) ile aynı yük altında karşılaştırdık; canlıya kademeli (canary) çıkardık ve metrikleri canlı izledik. Geri alma planı hazırlandı (index drop planı), ama gerek kalmadı.
  • Önleyici tedbirler: (1) CI'a sorgu planı kontrolü (regresyonda index'siz full scan alarmı), (2) connection pool ve p95 latency için alerting, (3) production'a çıkan her DB değişikliğinin "explain kontrolü" adımı, (4) postmortem dokümanı yazıp ekible paylaştık.
